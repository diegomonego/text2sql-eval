# text2sql-eval

Tools for evaluating a Text-to-SQL system with a small, fixed budget of test questions. There are three Claude Code skills:

| Skill | What it does |
|---|---|
| `generate-questions` | Writes exactly N realistic natural-language questions about a relational database, chosen to spread across tables, columns and query shapes. |
| `judge-correctness` | Judges each question: unrelated, on-topic but needing data the database lacks, ambiguous, or answerable. |
| `judge-coverage` | Measures how well the set covers tables, columns and query shapes, and where it repeats itself or leaves gaps. |

In every skill, the LLM reads questions and links phrases to the schema, and code checks every link against the database. Nothing here writes or runs SQL to answer the questions. The design and its trade-offs are in [DESIGN.md](DESIGN.md).

## Prerequisites

- macOS or Linux, with `make`.
- [uv](https://docs.astral.sh/uv/). It installs Python 3.12 and every dependency.
- [Claude Code](https://docs.claude.com/en/docs/claude-code) (the `claude` CLI), logged in with an account that can use `claude-opus-5-5`. Developed with Claude Code 2.1.331.
- Internet access for the first setup: DuckDB downloads its TPC-H extension, and `make docs` downloads the TPC-H specification.

**Credentials:** only your own Claude Code login, through `claude` itself (a Claude subscription or an `ANTHROPIC_API_KEY` in your environment). Nothing in this repository holds or needs credentials. `.env` and `.claude/settings.local.json` are gitignored.

## Setup

```bash
make setup   # uv sync: Python 3.12, DuckDB 2.0.1 and the other dependencies
make db      # builds data/tpch_sf01.duckdb (TPC-H, scale factor 0.1, about 29 MB), a few seconds
make docs    # downloads the TPC-H spec, checks its SHA-256, and extracts the sections the skills read, about 1-2 minutes
make test    # 62 self-tests; no LLM calls, no cost
```

To check that your copy matches the one used here, see [Reproducing the results](#reproducing-the-results).

### The database

| | |
|---|---|
| Engine | DuckDB 2.0.1, pinned in `pyproject.toml` |
| Dataset | TPC-H, generated by DuckDB's `tpch` extension: `INSTALL tpch; LOAD tpch; CALL dbgen(sf = 0.1);` |
| Size | 8 tables and 61 columns; `lineitem` has about 600,000 rows |
| Recreate | `make db`, or `uv run t2s db-build --benchmark tpch --sf 0.1 --out data/tpch_sf01.duckdb` |

The database file isn't committed. `uv run t2s db-info` prints what the tools discover: tables, row counts, joins, column notes, and a content fingerprint (`data_sha256`) for checking a rebuilt copy. The connection is a URL in `config/eval.toml` (`duckdb:///data/tpch_sf01.duckdb`), or the generator's `--db` argument.

### Semantic documentation

Every `.md` / `.txt` file under the configured docs folder (`semantic_docs/tpch`) is given to the generator and both judges:

- **`semantic_docs/tpch/glossary.md`**: business definitions written for this project and checked against the spec. Project conventions, such as the definition of revenue, are marked *convention*.
- **`semantic_docs/tpch/spec/*.md`**: extracts from the [TPC-H specification v3.0.1](https://www.tpc.org/TPC_Documents_Current_Versions/pdf/TPC-H_v3.0.1.pdf). They cover clauses 1.1–1.4 (logical database design) and 4.2.2–4.2.3 (data generation). `make docs` downloads the PDF, checks it against the SHA-256 in `config/eval.toml`, and writes the extracts. They aren't committed, because of the TPC license.

To supply other documents, pass `--docs <folder>` to the generator, or change `[docs] dir` in the config. To run without documents, pass `--no-docs`.

## Generating questions

```bash
make generate N=5 RUN=runs/my_n5
```

That runs the skill headless. The same thing without make:

```bash
claude -p "/generate-questions --n 5 --out runs/my_n5" \
  --permission-mode acceptEdits --allowedTools "Read,Write,Edit,Bash(uv run t2s *)"
```

To use it interactively, start `claude` in the repository root and type `/generate-questions --n 5 --out runs/my_n5`.

| Argument | Meaning |
|---|---|
| `--n <N>` | **Required.** Exactly how many questions to return, a positive integer. |
| `--out <folder>` | **Required.** Where to write the run. |
| `--db <url>` | Database connection, e.g. `duckdb:///data/tpch_sf01.duckdb`. Default: the config. |
| `--docs <folder>` / `--no-docs` | Documents to use, or none. Default: the config's docs folder. |
| `--preset coverage\|natural` | `coverage` (default) spreads questions across the schema. `natural` favors everyday questions: simpler, at most 2 shapes each, more free-form. |
| `--anchor auto\|off\|YYYY-MM-DD` | Reference date for relative phrases like "last quarter". `auto` uses the latest order date (1998-08-02). |

With make, pass the optional arguments as `PRESET=natural` or `GEN_ARGS='--no-docs'`. `CONFIG=<file>` switches to another config file, which is how the robustness runs below point at other databases.

**Output:** `questions.json`, with exactly N questions, each with a unique ID:

```json
{"questions": [
  {"id": "q01",
   "text": "How many customers in the MIDDLE EAST region have never placed an order?",
   "labels": {"tables": ["customer", "orders", "region"], "columns": ["region.r_name"],
              "shapes": ["aggregation", "anti_join", "multi_join"]}}
]}
```

`labels` are the generator's intended tables, columns and shapes. The judges never see them: they rebuild their own links from the text, and code compares the two. Next to `questions.json`, the `generation/` folder keeps everything needed to trace a run:

- the schema card and brief the LLM read;
- every candidate, with its checked links and why it was dropped or not picked (`pool.json`);
- every candidate's gain in every selection round (`pick_log.json`);
- selection diagnostics (`diagnostics.json`);
- run metadata (`run.json`).

A run costs about $1–1.40 with `claude-opus-5-5` and takes 2–5 minutes.

### How the generator works

1. **Discovery (code).** It reads tables and columns from DuckDB's `information_schema`, takes foreign keys from `duckdb_constraints()` when they're declared, and otherwise infers joins from column names and values (TPC-H declares none). It profiles every column (range, distinct values, constant or coded) into a schema card.
2. **Targets (code).** It sizes a pool of max(2N, 16) targeted slots, each asking for one query shape (with a focus table under the `coverage` preset), plus N free-form slots.
3. **Candidates (LLM).** One question per slot, written as a business user would ask it. Each phrase is linked to a table, a column (with its value for filters) or a query shape.
4. **Checks (code).** Every link is verified: the phrase is in the question, the table or column exists, the value exists in the data, and the tables connect. Failing candidates are dropped with a reason. Questions that differ only in their filter values count as duplicates.
5. **Selection (code).** Greedy selection picks exactly N for coverage of query shapes (half the weight), tables and columns (a quarter each). Shapes are weighted by how often analysts ask for them and how hard they are for systems. Each run reports how close greedy came to the best possible subset; on these pools it's 100%.

When the budget is small, query shapes come first, as the case 1 analysis shows. Different wordings of the same computation are caught as duplicates before selection, and again by the coverage judge's repetition check. Details and trade-offs are in [DESIGN.md](DESIGN.md).

## Judging questions

Each judge runs on its own, on any saved question list, including one a reviewer has edited.

```bash
make judge-correctness RUN=runs/my_n5   # judges runs/my_n5/questions.json -> correctness.json and correctness.md
make judge-coverage RUN=runs/my_n5      # -> coverage.json and coverage.md
make judges RUN=runs/my_n5              # both, one after the other
make check-run RUN=runs/my_n5           # checks that the run's files agree
```

The same thing without make (swap in `judge-coverage` for the other judge):

```bash
claude -p "/judge-correctness --questions runs/my_n5/questions.json --out runs/my_n5" \
  --permission-mode acceptEdits --allowedTools "Read,Write,Edit,Bash(uv run t2s *)" \
  --disallowedTools "Read(**/questions.json)"
```

To use one interactively, start `claude` in the repository root and type `/judge-correctness --questions runs/my_n5/questions.json --out runs/my_n5`.

| Argument | Meaning |
|---|---|
| `--questions <file>` | **Required.** The question list to judge. |
| `--out <folder>` | **Required.** Where to write the reports. |
| `--db <url>` / `--docs <folder>` / `--no-docs` | The database and documents. Default: the config. |
| `--anchor auto\|off\|YYYY-MM-DD` | Reference date for relative phrases. |

**Input.** Any JSON file of the form `{"questions": [{"id": "…", "text": "…"}, …]}` with unique IDs. `labels` (the generator's intended tables, columns and shapes) are optional. Any other field is dropped with a warning, so an edited file can't pass hidden hints to a judge.

**What a judge sees.** Only IDs and text. The prepare step writes a stripped copy, and reading any `questions.json` is blocked in judge runs. Each judge writes its own links from the text, and code checks them against the database. Code then compares those links with the labels, if any, and reports each label as confirmed, contradicted or not found. Labels never earn credit.

### Correctness judge

For each question it gives a verdict, a short rationale grounded in the schema or docs, and the checked links behind the verdict. The verdicts are tested in this order; the first that applies wins:

| Verdict | When | Evidence in the report |
|---|---|---|
| `OFF_TOPIC` | Not about the business in the database | The rationale |
| `MISSING_DATA` | On topic, but a concept has no data and can't be derived from existing columns | The missing concept, the closest columns, and why they don't fit |
| `AMBIGUOUS` | Two or more reasonable readings give materially different answers, and the docs don't settle it | Each reading, with its own checked links |
| `ANSWERABLE` | Every concept links to data, the tables connect, and there is one reading | The links |

**Score** = (ANSWERABLE + 0.5 × AMBIGUOUS) / N. The report lists the count of each verdict, so the score can be rebuilt by hand.

### Coverage judge

- **Eligible:** every table, every column and every shape in the legend (8, 61 and 8 for TPC-H).
- **Credit:** only from the judge's own links that passed the code checks and point to one target.
  - A phrase that could mean two columns earns nothing.
  - A question with a concept that has no data earns nothing at all.
- **The report, in this order:**
  1. covered / eligible per dimension, with every uncovered item listed (columns grouped by table);
  2. a budget note: how much coverage is possible at this N, and how many questions or phrases earned nothing;
  3. which questions cover each item;
  4. repetition: duplicate pairs, questions covering nothing unique, questions earning no credit;
  5. the summary score.

**Score** = (table % + column % + shape %) / 3.

**Exit codes.** The finalize step exits with code 2 for format problems and 3 for evidence problems (for example, a link that fails a check). The judge fixes its file and retries up to twice. Problems that remain are accepted with `--accept-issues` and flagged in the report.

A judge run costs about $0.50–0.75 with `claude-opus-5-5` and takes 1–2 minutes.

## Reproducing the results

### 1. Rebuild and check the inputs

```bash
make setup && make db && make docs && make test
uv run t2s db-info
```

`db-info` should print `"data_sha256": "2df9fef25352f1a5be0f2cb6428ed5b0ed5026fff544044cc338b9752fd77127"`. That's a hash of the data itself (row counts plus DuckDB's row hashes, independent of row order), so it matches on any machine running DuckDB 2.0.1. The database file's own SHA-256 (`file_sha256`) differs between builds even when the data is identical, so treat it as informational. Runs made before the content hash was added record only the file hash.

The spec extracts come out byte-identical. Their SHA-256s are recorded in every run's metadata, under `docs` in `generation/run.json` and in the judge reports' `meta`.

All of this was checked from scratch in an empty copy of the repository:
- `make db` took about 4 seconds;
- `make docs` took about 80 seconds, mostly the download;
- all tests passed;
- the data fingerprint and the spec extracts matched.

### 2. Rerun the judges on the saved question sets

The question files are saved, so judging is the part a reviewer can repeat exactly. Copy a file to a new folder first, so the saved reports aren't overwritten:

```bash
mkdir -p runs/rejudge_n15 && cp runs/v2_n15/questions.json runs/rejudge_n15/
make judges RUN=runs/rejudge_n15 && make check-run RUN=runs/rejudge_n15
```

The same works for case 1 (`runs/v2_n5`) and case 3 (`runs/v2_n15_controlled`). Expect the same verdicts and coverage: judging the case 2 file twice gave identical results. Only the wording of the judge's links varied.

To repeat the judge validation, copy `runs/labeled_20/questions.json` and `labels.json` to a new folder, run `make judge-correctness RUN=<folder>`, then `python3 validation/judge_agreement.py <folder>`. The saved run agreed on 19 of 20 (Cohen's κ 0.93).

### 3. Generate new sets

```bash
make pipeline N=5            # generate, judge and check: writes runs/new_n5
make pipeline N=15
make pipeline N=5 PRESET=natural RUN=runs/new_n5_natural
```

LLM output varies, so you'll get different questions, all passing the same checks. Runs are traceable, not repeatable: each run's `generation/` folder records why every question was picked or dropped. New runs go to `runs/new_*` by default and never overwrite the saved ones.

### 4. Robustness runs

```bash
make db SF=0.01 DB=data/tpch_sf001.duckdb                     # data_sha256 9fed7962d47211a15e5d0eea4f423b8235c8935509cc9dbae05cdc6a94f69e3a
make db BENCHMARK=tpcds SF=0.01 DB=data/tpcds_sf001.duckdb    # data_sha256 0da0edea5d0930bdf9355fe3aa4fb8a005187fa6e4985dfd76ba35c47a8b4075
make generate N=5 CONFIG=config/eval_tpch_sf001.toml RUN=runs/new_tpch_sf001_n5
make generate N=5 CONFIG=config/eval_tpcds.toml RUN=runs/new_tpcds_n5 GEN_ARGS=--no-docs
```

### 5. The BIRD calibration (optional)

```bash
uv sync --group calibration
mkdir -p downloads/bird_minidev && curl -sfL -o downloads/bird_minidev/mini_dev_sqlite_2025-07-04.json \
  https://huggingface.co/datasets/birdsql/bird_mini_dev/resolve/5b256b5a9c17478f06ed6912612e9a14d17065c8/archive/bird_mini_dev_2025-07-04/data/mini_dev_sqlite-00000-of-00001.json
uv run --group calibration python -I calibration/bird_i.py
```

This regenerates `calibration/bird_i_results.json`, whose `proposed_I` values are the I values in `config/shapes.toml`. The input file's SHA-256 is recorded in the results.

### Troubleshooting

- **`claude: command not found`:** install Claude Code and make sure its folder (usually `~/.local/bin`) is on your `PATH`. Opening a new terminal often fixes it.
- **uv warns that `VIRTUAL_ENV` doesn't match the project:** another project's virtual environment is active. Run `unset VIRTUAL_ENV`, or ignore the warning: uv uses this project's `.venv` anyway.
- **`make docs` can't download the spec:** download `TPC-H_v3.0.1.pdf` in a browser and save it as `downloads/TPC-H_v3.0.1.pdf`. `make docs` reuses the file and still checks its SHA-256.
- **`make db` fails on first use:** DuckDB downloads its `tpch` / `tpcds` extension the first time, which needs internet access.
- **No access to `claude-opus-5-5`:** set another model for each component under `[model]` in `config/eval.toml` and run `make skills`. Results will differ from the saved runs.
- **Permission prompts in interactive use:** `.claude/settings.json` pre-approves `uv run t2s *`. Approve file reads and writes when asked, or use the make targets, which run headless with the needed permissions.

## Disclosures

- **TPC-H's 22 benchmark queries** (spec clause 2) are not given to any component and are not used as examples. The LLM may still know them from training. Checking generated questions for overlap with them is out of scope for this version.
- **BIRD** (Li et al., 2023, *Can LLM Already Serve as a Database Interface? A BIg Bench for Large-Scale Database Grounded Text-to-SQLs*, NeurIPS 2023 Datasets and Benchmarks, https://arxiv.org/abs/2305.03111; data: [Mini-Dev](https://huggingface.co/datasets/birdsql/bird_mini_dev), CC BY-SA 4.0) was used offline, once, to set starting values for the query-shape difficulty weights (`calibration/bird_i.py`, results in `calibration/bird_i_results.json`). It reads BIRD's existing SQL to tag each question's shapes. BIRD questions are never given to the generator.
